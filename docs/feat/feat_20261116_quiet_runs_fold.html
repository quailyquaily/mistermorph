Folding the runs of a TODO item that found nothing to do

A TODO item on a schedule often runs and finds nothing to do. Each such run still adds a full message pair to the item's topic, so the runs that did something are hard to find. This note proposes a check that marks those runs, and a fold that draws them as one line.

Goal

  • After a scheduled run, decide whether it had a result, found nothing to do, or hit a problem.
  • In the item's topic, draw consecutive "nothing to do" runs as one line that opens.
  • Hide nothing for good: a folded run is still stored and can always be opened.

The check

When a scheduled run finishes, ask the decision route one closed question about it, and store the answer on the run's record beside result.final.

PartProposal
QuestionOne Choice through llm.Evaluate, with the item's task text and the run's final output as State. Options: result (it did or found something), nothing (it found nothing to do), problem (it could not do its job).
Which runsRuns a schedule fired that ended done. Failed, stopped and manual runs are not checked and never fold.
When it cannot answerThe run is shown in full, as today: when the decision route has no profile of its own, when the call fails, or when the answer is not one of the options.
WhererecordAwarenessTaskFinish in internal/channelruntime/awareness/run.go writes the result. Awareness runs do not get the decision client today; it is passed in the way taskruntime passes it for todo_update.
Stored asresult.outcome: "result", "nothing" or "problem"; absent when the run was not checked.

This meets the three criteria in Other fits for the decision route: the answer is a closed set, the model writes no text, and a wrong answer is survivable, since it only folds a message that can be opened.

The run's own model could mark itself instead, at no extra call. That depends on every task prompt and skill doing so; the check after the run works for any item.

How it is drawn

  • Folded. One centred line in mono: a hollow status dot, the count ("8 runs, nothing to do"), the time span, and a caret. It takes the hover tint under the pointer.
  • Open. The line stays. Under it each quiet run is one row: its time, and its reply cut to one line, hung on a faint vertical rule. The task bubble is not repeated, since it is the same text every run.
  • No new element. The line is the context-compaction notice's centred mono row (chat-context-notice in ChatHistoryItem.tsx) made pressable. The caret, the hover and the vertical rule are the Agent Link exchange's fold (ChatAgentLinkExchange.tsx). Colours and type are the Console's tokens.

Rules

  • Consecutive nothing runs form one group. A result or problem run, a manual run, or an unchecked run ends the group and is shown in full.
  • One quiet run folds too ("1 run, nothing to do"), so the topic looks the same whatever the count.
  • A run still in progress is shown in full; it joins a group only once it is checked.
  • Whether a group is open is the page's state, kept per group like the other folds (ChatRowContext.folds), since rows recycle.

Around the topic

  • TODO list in the sidebar. A nothing run does not move the topic up or mark it unread; the topic's second row is unchanged.
  • Notifications. A nothing run raises none.

Open choices

  • Reading one quiet run in full. Not drawn. The simplest choice: pressing a row shows that run as it looks today, in place.
  • Three answers or two. problem keeps "could not reach GitHub" from folding with "new/ is empty". A Boolean is enough if that case is left to the run failing.
  • Runs from before the check. Left unchecked and shown in full; no backfill.
  • Cost. One small call per scheduled run on the decision profile.

Not in scope

  • Deleting or pruning quiet runs.
  • Folding in the Awareness topic (heartbeat runs) or in other channels.
